# Modelo de datos

Fuente de verdad del esquema. Modelos (`app/models/*.py`) y la migración inicial
(`migrations/versions/*_0001_initial_schema.py`) deben coincidir **exactamente** con esto.
Validación: `alembic check` no debe reportar diferencias (ver TESTING.md).

```
users 1───N fields 1───N weather_forecasts
               │
               1
               │
               N
            alerts 1───N notifications
```

## Convenciones

- PK: `id BIGINT GENERATED BY DEFAULT AS IDENTITY` → en SQLAlchemy `mapped_column(BigInteger, Identity(), primary_key=True)`.
- FKs: `BIGINT`, `NOT NULL`, `ON DELETE CASCADE` (en el modelo: `ForeignKey("x.id", ondelete="CASCADE")`).
- Timestamps: `TIMESTAMPTZ`, `server_default now()` → usar `TimestampMixin` de `app/models/base.py`.
- Nombres de constraints: los genera la naming convention de `Base.metadata`
  (no hardcodear nombres salvo los CHECK, que requieren `name=`).
- Probabilidades y umbrales: **enteros 0..100 (porcentaje)** en `SMALLINT`. Evita problemas de
  precisión con floats y es lo que se le muestra al usuario.
- Fechas de pronóstico: `DATE` (el pronóstico es diario).

### Enums

`EventType` y `NotificationStatus` (`app/models/enums.py`) se persisten como **`VARCHAR` + CHECK**, no
como `ENUM` nativo de Postgres:

```python
mapped_column(
    SAEnum(
        EventType,
        native_enum=False,
        length=32,
        validate_strings=True,
        values_callable=lambda e: [m.value for m in e],
        create_constraint=True,
        name="event_type",
    ),
    nullable=False,
)
```

Motivo: agregar un tipo de evento nuevo es una migración trivial (recrear el CHECK) y no requiere
`ALTER TYPE ... ADD VALUE` (que no corre dentro de transacción en versiones viejas de PG).
`values_callable` es obligatorio: se guarda el **value** (`"frost"`), no el nombre (`"FROST"`).

Valores:
- `event_type`: `frost`, `rain`, `hail`, `strong_wind`, `heat_wave`
- `notification_status`: `pending`, `sent`, `failed`

## users

Usuario de Agrobot. En producción se identifica por su número de WhatsApp.

| columna      | tipo          | null | default | notas                                     |
|--------------|---------------|------|---------|-------------------------------------------|
| id           | BIGINT        | no   | identity| PK                                        |
| phone_number | VARCHAR(20)   | no   |         | E.164 (`+5491122334455`), **UNIQUE**      |
| name         | VARCHAR(120)  | no   |         |                                           |
| created_at   | TIMESTAMPTZ   | no   | now()   |                                           |
| updated_at   | TIMESTAMPTZ   | no   | now()   |                                           |

Constraints: `UNIQUE (phone_number)`; CHECK `phone_number ~ '^\+[1-9][0-9]{7,14}$'` (name=`phone_number_e164`,
migración `0002`): el formato E.164 lo garantiza la DB, así el UNIQUE es unicidad real del número.

## fields

Campo (lote/establecimiento) de un usuario.

| columna    | tipo          | null | notas                                   |
|------------|---------------|------|-----------------------------------------|
| id         | BIGINT        | no   | PK                                      |
| user_id    | BIGINT        | no   | FK → users.id ON DELETE CASCADE         |
| name       | VARCHAR(120)  | no   |                                         |
| latitude   | NUMERIC(9,6)  | no   | CHECK `latitude BETWEEN -90 AND 90` (name=`latitude_range`)     |
| longitude  | NUMERIC(9,6)  | no   | CHECK `longitude BETWEEN -180 AND 180` (name=`longitude_range`) |
| created_at | TIMESTAMPTZ   | no   |                                         |
| updated_at | TIMESTAMPTZ   | no   |                                         |

Constraints: `UNIQUE (user_id, name)`. Índice: implícito por el UNIQUE (cubre búsquedas por `user_id`).

## weather_forecasts

**Tabla que alimenta el job de ingesta existente** (mockeado en este repo). Una fila por
(campo, día, tipo de evento) con la probabilidad vigente; la ingesta hace *upsert*, así que siempre
refleja el último pronóstico.

| columna       | tipo          | null | notas                                                      |
|---------------|---------------|------|------------------------------------------------------------|
| id            | BIGINT        | no   | PK                                                         |
| field_id      | BIGINT        | no   | FK → fields.id ON DELETE CASCADE                           |
| forecast_date | DATE          | no   | día pronosticado                                           |
| event_type    | VARCHAR(32)   | no   | CHECK enum `event_type`                                    |
| probability   | SMALLINT      | no   | CHECK `probability BETWEEN 0 AND 100` (name=`probability_range`) |
| source        | VARCHAR(50)   | no   | proveedor que lo informó (ej. `mock`)                      |
| fetched_at    | TIMESTAMPTZ   | no   | cuándo lo obtuvo la ingesta                                |
| created_at    | TIMESTAMPTZ   | no   |                                                            |
| updated_at    | TIMESTAMPTZ   | no   |                                                            |

Constraints / índices:
- `UNIQUE (field_id, forecast_date, event_type)` → clave natural, target del upsert y del JOIN del
  evaluador (el índice del UNIQUE empieza por `field_id`, que es como joinea el evaluador).

> Decisión: el pronóstico se guarda **por campo** (la ingesta resuelve lat/long → pronóstico).
> Alternativa a futuro: tabla de `locations`/grilla compartida entre campos cercanos para no
> duplicar pronósticos. Documentado en README §Decisiones.

## alerts

Configuración del usuario: "avisame cuando la probabilidad de `event_type` en `field` sea ≥ `threshold`".

| columna    | tipo        | null | default | notas                                                    |
|------------|-------------|------|---------|----------------------------------------------------------|
| id         | BIGINT      | no   |         | PK                                                       |
| field_id   | BIGINT      | no   |         | FK → fields.id ON DELETE CASCADE                         |
| event_type | VARCHAR(32) | no   |         | CHECK enum `event_type`                                  |
| threshold  | SMALLINT    | no   |         | CHECK `threshold BETWEEN 1 AND 100` (name=`threshold_range`) |
| is_active  | BOOLEAN     | no   | true    | `server_default=sa.true()`                               |
| created_at | TIMESTAMPTZ | no   |         |                                                          |
| updated_at | TIMESTAMPTZ | no   |         |                                                          |

Constraints / índices:
- `UNIQUE (field_id, event_type)` → una alerta por evento por campo; para cambiar el umbral se usa PATCH.
- Índice parcial `ix_alerts_active_field_event` en `(field_id, event_type) WHERE is_active`
  (lo usa el evaluador). En el modelo:
  `Index("ix_alerts_active_field_event", "field_id", "event_type", postgresql_where=text("is_active"))`.

> El dueño de la alerta se deriva de `fields.user_id` (no se duplica `user_id` en `alerts`:
> imposible que queden inconsistentes).

## notifications

Outbox de notificaciones. La crea el evaluador y la consume el dispatcher.
Guarda un **snapshot** de los valores que dispararon la alerta (el forecast puede cambiar luego).

| columna         | tipo        | null | default   | notas                                                     |
|-----------------|-------------|------|-----------|-----------------------------------------------------------|
| id              | BIGINT      | no   |           | PK                                                        |
| alert_id        | BIGINT      | no   |           | FK → alerts.id ON DELETE CASCADE                          |
| forecast_date   | DATE        | no   |           | día del evento                                            |
| event_type      | VARCHAR(32) | no   |           | snapshot, CHECK enum `event_type`                         |
| probability     | SMALLINT    | no   |           | snapshot, CHECK 0..100 (name=`probability_range`)         |
| threshold       | SMALLINT    | no   |           | snapshot del umbral al momento de disparar, CHECK 1..100 (name=`threshold_range`) |
| status          | VARCHAR(16) | no   | 'pending' | CHECK enum `notification_status`                          |
| attempts        | SMALLINT    | no   | 0         | CHECK `attempts >= 0` (name=`attempts_non_negative`)      |
| last_error      | TEXT        | sí   |           | último error del notifier; CHECK `last_error IS NULL OR char_length(last_error) <= 1000` (name=`last_error_length`, migración `0002`) |
| next_attempt_at | TIMESTAMPTZ | no   | now()     | no se reintenta antes de esta fecha (backoff)             |
| sent_at         | TIMESTAMPTZ | sí   |           | seteado cuando status = sent                              |
| created_at      | TIMESTAMPTZ | no   |           |                                                           |
| updated_at      | TIMESTAMPTZ | no   |           |                                                           |

Constraints / índices:
- `UNIQUE (alert_id, forecast_date)` → **idempotencia / deduplicación**: como máximo una
  notificación por alerta por día pronosticado, aunque el job corra N veces o en N réplicas.
- Índice parcial `ix_notifications_pending_due` en `(next_attempt_at) WHERE status = 'pending'`
  (cola del dispatcher; queda chico porque solo indexa pendientes).
- Índice `ix_notifications_alert_id_created_at` en `(alert_id, created_at)` (listado por usuario).
  El UNIQUE `(alert_id, forecast_date)` ya cubre búsquedas por `alert_id`, así que este es opcional;
  incluirlo.

## Migración 0002 — hardening (S2)

- Archivo `migrations/versions/<fecha>_0002_constraints_hardening.py`, `revision = "0002"`, `down_revision = "0001"`.
- `op.create_check_constraint("phone_number_e164", "users", ...)` y `op.create_check_constraint("last_error_length", "notifications", ...)`
  (la naming convention los convierte en `ck_users_phone_number_e164` / `ck_notifications_last_error_length`).
- `downgrade()` los elimina con `op.drop_constraint(..., type_="check")` usando el nombre final.
- Agregar los mismos `CheckConstraint` a los modelos `User` y `Notification`.

## Migración inicial (S1)

- Archivo: `migrations/versions/<fecha>_0001_initial_schema.py`, `revision = "0001"`,
  `down_revision = None`. Crear con `make migration m="initial schema"` y editar el `revision` a `"0001"`.
- Escribirla **a mano** con `op.create_table` / `op.create_index` (no confiar ciegamente en
  autogenerate; se puede usar como borrador y revisar).
- Orden de creación: users → fields → weather_forecasts → alerts → notifications.
- `downgrade()` borra en orden inverso. Debe funcionar (los tests hacen `downgrade base`).
- Después de escribirla: `make db-up && make migrate && uv run alembic check` → "No new upgrade
  operations detected."
