# Modelo de datos

Fuente de verdad del esquema. Modelos (`app/models/*.py`) y la migración inicial
(`migrations/versions/*_0001_initial_schema.py`) deben coincidir **exactamente** con esto.
Validación: `alembic check` no debe reportar diferencias (ver TESTING.md).

```
users 1───N fields 1───N weather_forecasts
               │
               1
               │
               N
            alerts 1───N notifications
               │
               1───N alert_day_states
```

## Convenciones

- PK: `id BIGINT GENERATED BY DEFAULT AS IDENTITY` → en SQLAlchemy `mapped_column(BigInteger, Identity(), primary_key=True)`.
- FKs: `BIGINT`, `NOT NULL`, `ON DELETE CASCADE` (en el modelo: `ForeignKey("x.id", ondelete="CASCADE")`).
- Timestamps: `TIMESTAMPTZ`, `server_default now()` → usar `TimestampMixin` de `app/models/base.py`.
- Nombres de constraints: los genera la naming convention de `Base.metadata`
  (no hardcodear nombres salvo los CHECK, que requieren `name=`).
- Probabilidades y umbrales: **enteros 0..100 (porcentaje)** en `SMALLINT`. Evita problemas de
  precisión con floats y es lo que se le muestra al usuario.
- Fechas de pronóstico: `DATE` (el pronóstico es diario).

### Enums

`EventType` y `NotificationStatus` (`app/models/enums.py`) se persisten como **`VARCHAR` + CHECK**, no
como `ENUM` nativo de Postgres:

```python
mapped_column(
    SAEnum(
        EventType,
        native_enum=False,
        length=32,
        validate_strings=True,
        values_callable=lambda e: [m.value for m in e],
        create_constraint=True,
        name="event_type",
    ),
    nullable=False,
)
```

Motivo: agregar un tipo de evento nuevo es una migración trivial (recrear el CHECK) y no requiere
`ALTER TYPE ... ADD VALUE` (que no corre dentro de transacción en versiones viejas de PG).
`values_callable` es obligatorio: se guarda el **value** (`"frost"`), no el nombre (`"FROST"`).

Valores:
- `event_type`: `frost`, `rain`, `hail`, `strong_wind`, `heat_wave`
- `notification_status`: `pending`, `sent`, `failed`, `cancelled` (S9: ya no correspondía enviarla)

## users

Usuario de Agrobot. En producción se identifica por su número de WhatsApp.

| columna      | tipo          | null | default | notas                                     |
|--------------|---------------|------|---------|-------------------------------------------|
| id           | BIGINT        | no   | identity| PK                                        |
| phone_number | VARCHAR(20)   | no   |         | E.164 (`+5491100000001`), **UNIQUE**      |
| name         | VARCHAR(120)  | no   |         |                                           |
| timezone     | VARCHAR(64)   | no   | 'America/Argentina/Buenos_Aires' | zona IANA del usuario; define su horario de silencio (S13, migración 0009). Se valida igual que `fields.timezone` |
| quiet_hours_start | TIME     | sí   |         | inicio del horario de silencio, hora local (S13) |
| quiet_hours_end   | TIME     | sí   |         | fin (excluido) del horario de silencio; si es menor que el inicio, cruza la medianoche (S13) |
| created_at   | TIMESTAMPTZ   | no   | now()   |                                           |
| updated_at   | TIMESTAMPTZ   | no   | now()   |                                           |

Constraints: `UNIQUE (phone_number)`; CHECK `phone_number ~ '^\+[1-9][0-9]{7,14}$'` (name=`phone_number_e164`,
migración `0002`): el formato E.164 lo garantiza la DB, así el UNIQUE es unicidad real del número.
CHECK `(quiet_hours_start IS NULL) = (quiet_hours_end IS NULL)` (name=`quiet_hours_both_or_none`) y
CHECK `quiet_hours_start <> quiet_hours_end` (name=`quiet_hours_not_empty`) (migración `0009`): o se
configuran los dos extremos o ninguno, y una ventana vacía no tiene sentido.

## fields

Campo (lote/establecimiento) de un usuario.

| columna    | tipo          | null | notas                                   |
|------------|---------------|------|-----------------------------------------|
| id         | BIGINT        | no   | PK                                      |
| user_id    | BIGINT        | no   | FK → users.id ON DELETE CASCADE         |
| name       | VARCHAR(120)  | no   |                                         |
| latitude   | NUMERIC(9,6)  | no   | CHECK `latitude BETWEEN -90 AND 90` (name=`latitude_range`)     |
| longitude  | NUMERIC(9,6)  | no   | CHECK `longitude BETWEEN -180 AND 180` (name=`longitude_range`) |
| timezone   | VARCHAR(64)   | no   | zona IANA del campo (default `America/Argentina/Buenos_Aires`); define el "hoy" local del campo (S12a, migración 0007). Se valida en la API con `zoneinfo` |
| created_at | TIMESTAMPTZ   | no   |                                         |
| updated_at | TIMESTAMPTZ   | no   |                                         |

Constraints: `UNIQUE (user_id, name)`. Índice: implícito por el UNIQUE (cubre búsquedas por `user_id`).

## weather_forecasts

**Tabla que alimenta el job de ingesta existente** (mockeado en este repo). Una fila por
(campo, día, tipo de evento) con la probabilidad vigente; la ingesta hace *upsert*, así que siempre
refleja el último pronóstico.

| columna       | tipo          | null | notas                                                      |
|---------------|---------------|------|------------------------------------------------------------|
| id            | BIGINT        | no   | PK                                                         |
| field_id      | BIGINT        | no   | FK → fields.id ON DELETE CASCADE                           |
| forecast_date | DATE          | no   | día pronosticado                                           |
| event_type    | VARCHAR(32)   | no   | CHECK enum `event_type`                                    |
| probability   | SMALLINT      | no   | CHECK `probability BETWEEN 0 AND 100` (name=`probability_range`) |
| source        | VARCHAR(50)   | no   | proveedor que lo informó (ej. `mock`)                      |
| issued_at     | TIMESTAMPTZ   | no   | cuándo lo **emitió el proveedor** (corrida del modelo). Mide la frescura del dato y ordena las actualizaciones (S11, migración 0005) |
| fetched_at    | TIMESTAMPTZ   | no   | cuándo lo obtuvo la ingesta                                |
| created_at    | TIMESTAMPTZ   | no   |                                                            |
| updated_at    | TIMESTAMPTZ   | no   |                                                            |

Constraints / índices:
- `UNIQUE (field_id, forecast_date, event_type)` → clave natural, target del upsert y del JOIN del
  evaluador (el índice del UNIQUE empieza por `field_id`, que es como joinea el evaluador).

> Decisión: el pronóstico se guarda **por campo** (la ingesta resuelve lat/long → pronóstico).
> Alternativa a futuro: tabla de `locations`/grilla compartida entre campos cercanos para no
> duplicar pronósticos. Documentado en README §Decisiones.

## alerts

Configuración del usuario: "avisame cuando la probabilidad de `event_type` en `field` sea ≥ `threshold`".

| columna    | tipo        | null | default | notas                                                    |
|------------|-------------|------|---------|----------------------------------------------------------|
| id         | BIGINT      | no   |         | PK                                                       |
| field_id   | BIGINT      | no   |         | FK → fields.id ON DELETE CASCADE                         |
| event_type | VARCHAR(32) | no   |         | CHECK enum `event_type`                                  |
| threshold  | SMALLINT    | no   |         | CHECK `threshold BETWEEN 1 AND 100` (name=`threshold_range`) |
| is_active  | BOOLEAN     | no   | true    | `server_default=sa.true()`                               |
| created_at | TIMESTAMPTZ | no   |         |                                                          |
| updated_at | TIMESTAMPTZ | no   |         |                                                          |

Constraints / índices:
- `deleted_at TIMESTAMPTZ NULL` (S9, migración 0003): borrado lógico. Una alerta borrada no se lista, no se evalúa y no se puede modificar; su historial de notificaciones se conserva.
- **Índice único parcial** `uq_alerts_field_event_threshold_alive` en
  `(field_id, event_type, threshold) WHERE deleted_at IS NULL` (migración 0003):
  varias alertas por evento con umbrales distintos; una borrada se puede recrear.
- Índice parcial `ix_alerts_active_field_event` en `(field_id, event_type) WHERE is_active AND deleted_at IS NULL` (0003)
  (lo usa el evaluador). En el modelo:
  `Index("ix_alerts_active_field_event", "field_id", "event_type", postgresql_where=text("is_active AND deleted_at IS NULL"))`.

> El dueño de la alerta se deriva de `fields.user_id` (no se duplica `user_id` en `alerts`:
> imposible que queden inconsistentes).

## notifications

Outbox de notificaciones. La crea el evaluador y la consume el dispatcher.
Guarda un **snapshot** de los valores que dispararon la alerta (el forecast puede cambiar luego).

| columna         | tipo        | null | default   | notas                                                     |
|-----------------|-------------|------|-----------|-----------------------------------------------------------|
| id              | BIGINT      | no   |           | PK                                                        |
| alert_id        | BIGINT      | no   |           | FK → alerts.id ON DELETE CASCADE                          |
| forecast_date   | DATE        | no   |           | día del evento                                            |
| event_type      | VARCHAR(32) | no   |           | snapshot, CHECK enum `event_type`                         |
| probability     | SMALLINT    | no   |           | snapshot, CHECK 0..100 (name=`probability_range`)         |
| threshold       | SMALLINT    | no   |           | snapshot del umbral al momento de disparar, CHECK 1..100 (name=`threshold_range`) |
| episode         | INTEGER     | no   | 1         | número de episodio del (alerta, día) que la generó (S12b, D1). CHECK `episode >= 1` (name=`episode_positive`) |
| status          | VARCHAR(16) | no   | 'pending' | CHECK enum `notification_status`                          |
| attempts        | SMALLINT    | no   | 0         | CHECK `attempts >= 0` (name=`attempts_non_negative`)      |
| last_error      | TEXT        | sí   |           | último error del notifier; CHECK `last_error IS NULL OR char_length(last_error) <= 1000` (name=`last_error_length`, migración `0002`) |
| next_attempt_at | TIMESTAMPTZ | no   | now()     | doble uso, sin columnas extra: (1) **backoff**: no se reintenta antes de esta fecha; (2) **lease** del dispatcher: al reclamar se corre a `now + lease` (nadie más la toma) y su valor exacto es el **token de propiedad** para registrar el resultado. Ver JOBS.md §Dispatcher |
| sent_at         | TIMESTAMPTZ | sí   |           | seteado cuando status = sent                              |
| created_at      | TIMESTAMPTZ | no   |           |                                                           |
| updated_at      | TIMESTAMPTZ | no   |           |                                                           |

Constraints / índices:
- `UNIQUE (alert_id, forecast_date, episode)` (S12b, migración 0008) → **idempotencia /
  deduplicación**: como máximo una notificación por alerta, día pronosticado y episodio, aunque el
  job corra N veces o en N réplicas.
- Índice parcial `ix_notifications_pending_due` en `(next_attempt_at) WHERE status = 'pending'`
  (cola del dispatcher; queda chico porque solo indexa pendientes).
- Índice `ix_notifications_alert_id_created_at` en `(alert_id, created_at)` (listado por usuario).
  El UNIQUE `(alert_id, forecast_date, episode)` ya cubre búsquedas por `alert_id`, así que este es
  opcional; incluirlo.

## alert_day_states (S12b, D1)

Estado de episodio por (alerta, día pronosticado). Lo escribe el evaluador y lo re-arma el service
de alertas. **No hay fila = armada, episodio 0** (nunca disparó para ese día).

| columna       | tipo        | null | default | notas                                                     |
|---------------|-------------|------|---------|-----------------------------------------------------------|
| id            | BIGINT      | no   | identity| PK                                                        |
| alert_id      | BIGINT      | no   |         | FK → alerts.id ON DELETE CASCADE                          |
| forecast_date | DATE        | no   |         | día pronosticado                                          |
| episode       | INTEGER     | no   |         | último episodio disparado; CHECK `episode >= 1` (name=`episode_positive`) |
| armed         | BOOLEAN     | no   |         | `false` = disparó y sigue arriba (no se repite); `true` = el próximo cruce hacia arriba dispara el episodio `episode + 1` |
| created_at    | TIMESTAMPTZ | no   | now()   |                                                           |
| updated_at    | TIMESTAMPTZ | no   | now()   |                                                           |

Constraints / índices: `UNIQUE (alert_id, forecast_date)` (target del upsert del evaluador; cubre
las búsquedas por `alert_id` del re-armado). Modelo: `app/models/alert_day_state.py`, clase
`AlertDayState`.

> Las filas de días pasados no se borran (no hay job de retención).

## Migración 0009 — horario de silencio por usuario (S13)

  `down_revision = "0008"`.
- `users.timezone VARCHAR(64) NOT NULL DEFAULT 'America/Argentina/Buenos_Aires'` (server default:
  las filas existentes la toman sin backfill).
- `users.quiet_hours_start TIME NULL`, `users.quiet_hours_end TIME NULL` (sin silencio por defecto).
- CHECKs `quiet_hours_both_or_none` y `quiet_hours_not_empty` (tabla de arriba; la naming
  convention los convierte en `ck_users_quiet_hours_both_or_none` / `ck_users_quiet_hours_not_empty`).
- `downgrade()`: elimina los CHECK y las tres columnas.
- Modelo `User`: mismas columnas (`Mapped[time | None]` para las horas) y `CheckConstraint`s;
  `alembic check` limpio.

## Migración 0008 — episodios de notificación (S12b)

- `revision = "0008"`, `down_revision = "0007"`.
- Crea `alert_day_states` (tabla de arriba).
- `notifications.episode INTEGER NOT NULL DEFAULT 1` + CHECK `episode_positive`; las filas
  existentes quedan en episodio 1.
- Drop `uq_notifications_alert_id_forecast_date`; create `UNIQUE (alert_id, forecast_date, episode)`
  (nombre por naming convention: `uq_notifications_alert_id_forecast_date_episode`).
- **Backfill:** una fila en `alert_day_states` por cada (alert_id, forecast_date) que ya tiene
  notificaciones, con `episode = max(episode)` y `armed = false`. Así el despliegue no re-avisa días
  ya notificados: se comportan como un episodio en curso.
- `downgrade()`: si existe alguna notificación con `episode > 1`, falla con un mensaje claro (no
  borra datos en silencio); si no, recrea el UNIQUE `(alert_id, forecast_date)`, elimina la columna
  y la tabla.

## Migración 0005 — frescura de pronósticos (S11)

- `revision = "0005"`, `down_revision = "0004"`.
- `weather_forecasts.issued_at TIMESTAMPTZ`: se agrega nullable, se completa con `fetched_at` para
  las filas existentes y se pasa a `NOT NULL`.

  bloquear la tabla (con el volumen del challenge la versión directa tarda segundos).

## Migración 0003 — alertas: borrado lógico y varios umbrales (S9)

- `revision = "0003"`, `down_revision = "0002"`.
- `alerts.deleted_at` (TIMESTAMPTZ NULL).
- Drop `uq_alerts_field_id_event_type`; create unique index `uq_alerts_field_event_threshold_alive`
  `(field_id, event_type, threshold) WHERE deleted_at IS NULL`.
- Recrear `ix_alerts_active_field_event` con predicado `is_active AND deleted_at IS NULL`.
- Recrear los CHECK de `notifications.status` con el valor nuevo `cancelled`.
- En producción con tablas grandes: crear el índice con `CREATE UNIQUE INDEX CONCURRENTLY` y el CHECK
  con `NOT VALID` + `VALIDATE CONSTRAINT` para no bloquear escrituras (con el volumen del challenge
  la versión transaccional es instantánea).
- `downgrade()`: revierte todo; si hay alertas duplicadas vivas por (campo, evento) o notificaciones
  `cancelled`, el downgrade falla con un mensaje claro (no borra datos en silencio).

## Migración inicial (S1)

- Archivo: `migrations/versions/<fecha>_0001_initial_schema.py`, `revision = "0001"`,
  `down_revision = None`. Crear con `make migration m="initial schema"` y editar el `revision` a `"0001"`.
- Escribirla **a mano** con `op.create_table` / `op.create_index` (no confiar ciegamente en
  autogenerate; se puede usar como borrador y revisar).
- Orden de creación: users → fields → weather_forecasts → alerts → notifications.
- `downgrade()` borra en orden inverso. Debe funcionar (los tests hacen `downgrade base`).
- Después de escribirla: `make db-up && make migrate && uv run alembic check` → "No new upgrade
  operations detected."
